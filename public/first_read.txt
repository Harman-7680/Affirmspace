# AffirmSpace – Developer README

## 1. Project Overview

AffirmSpace is a multi-role web application and social/community platform built on Laravel.

The platform combines:

* Social networking
* Friendship and followers
* Dating
* Real-time/chat functionality
* Counselor services
* Events and event-based conversations
* Thoughts/posts
* Notifications
* Video calling
* Blog/content management
* Payments
* Admin management
* LGBTQ+ community and support features

The project supports three primary user roles with clearly separated responsibilities, views, controllers, permissions, and layouts.

### User Roles

* **Admin (`role = 2`)**

  * Full platform-level control
  * User management
  * Counselor management
  * Content/blog management
  * Event/content moderation
  * Payment/platform management
  * Administrative dashboards and settings

* **Counselor (`role = 1`)**

  * Professional users who provide counseling/support services
  * Counselor profile and specialization
  * Pricing
  * Ratings
  * Availability
  * Counselor requests
  * Counselee communication
  * Video sessions
  * Counselor-specific dashboard and functionality

* **Counselee / Normal User (`role = 0`)**

  * Normal registered users
  * Profile management
  * Social feed
  * Posts and thoughts
  * Likes, comments and replies
  * Friendship/following
  * Dating
  * Messaging
  * Events
  * Counselor discovery and requests
  * Notifications

### User Status

* `status = 1` → Active
* `status = 0` → Deactivated

### Counselor Verification

Counselor records use:

* `documents_status = 3` → Verified/approved counselor state used by the application

The exact status meanings should always be checked against the current controller/model logic before modifying verification workflows.

# 5. Routing Strategy

Primary web routes are defined in:

```text
routes/web.php
```

API routes are defined separately where applicable:

```text
routes/api.php
```

Routes are logically organized around:

* Authentication
* User/profile functionality
* Social features
* Friends/followers
* Posts
* Thoughts
* Dating
* Messaging
* Counselors
* Events
* Event chat
* Notifications
* Payments
* Admin
* Blogs

Laravel 11 uses `bootstrap/app.php` for application bootstrapping and middleware/API configuration rather than relying on the older `RouteServiceProvider.php` structure.

### Important Rule

Do not assume that URL parameters alone provide authorization.

For protected resources such as:

* Profiles
* Messages
* Event chats
* Counselor conversations
* Private content

the controller must verify that the authenticated user is actually authorized to access the requested resource.

# 6. Controller Design Philosophy

Controllers are organized according to feature responsibility.

Examples:

* `ProfileController` → Profile/feed/profile visibility logic
* `CounselorController` → Counselor functionality
* Event-related controllers → Event management and event conversations
* Admin controllers → Administrative functionality
* API controllers → Application/API requests

Existing working functionality should not be unnecessarily refactored while fixing an isolated issue.

For example, when modifying social interactions, preserve existing:

* Like logic
* Comment logic
* Reply logic
* Boost logic
* Notification logic

unless the change specifically requires modifying them.

# 20. Event Chat

Event conversations are **event-specific**.

A conversation must be identified using the combination of:

```text
event_id
other_user_id
```

and the authenticated user.

### Important Security Rule

Never retrieve event conversations only by `user_id`.

The selected event must first be verified as accessible/approved.

### Owner Case

If the authenticated user owns the event:

* The selected other user must actually have sent a message on that event.

### Visitor Case

If the authenticated user is not the event owner:

* The selected other user must be the event owner.
* The authenticated user must have actually sent a message on that event.

The final message query must be restricted to:

* Current authenticated user
* Selected user
* Selected event

This prevents messages belonging to another event or another conversation from appearing accidentally.

# 21. Jitsi Video Calling

Jitsi is used for video meetings/calls.

The application uses deterministic room naming for two-user calls.

Existing room format:

```text
AffirmSpaceCall_{min_user_id}_{max_user_id}
```

Using the minimum and maximum user IDs ensures that:

```text
User A → User B
```

and:

```text
User B → User A
```

produce the same room identifier.

Authorization should still be checked before allowing a user to join a protected call.

# 32. Security & Authorization Rules

Security is especially important for AffirmSpace because the application contains private social and communication data.

Always validate authorization server-side for:

* Profiles
* Posts
* Messages
* Event chats
* Counselor conversations
* Dating conversations
* Private content
* Admin pages
* Payments
* Video calls

Never assume that hiding a button or URL parameter provides security.

For example:

```text
/events/chats?event_id=45&user_id=197
```

must not automatically grant access to that event conversation.

The controller must verify the authenticated user's relationship to:

* Event
* Selected user
* Conversation

# 33. Feed & Data Performance

The feed can contain large relational datasets.

Example:

```text
Post
 ├── User
 ├── Likes
 ├── Comments
 │    └── Replies
 └── Boost information
```

Avoid loading every relation for every post when it is unnecessary.

Use:

* Pagination
* Lazy loading where appropriate
* Eager loading only required relationships
* Counts
* Current-user interaction state
* Load More
* Search pagination

For large user datasets, avoid sending every user record to the browser unnecessarily.

# 35. Feed Ordering & Boosts


When modifying feed ordering:

* Do not break Load More.
* Do not introduce duplicate posts.
